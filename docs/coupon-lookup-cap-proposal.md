# 쿠폰 코드 조회 — 전체 계정 합산 상한과 계정 확인 방식 (제안)

> 2026-09-11. 사용자 질문: "전체 계정 합산 상한을 두려면 어떤 식으로 계정 확인을 할 수 있을까?"
> 조사 2개(계정 신호 전수조사 · 인프라 선택지) + 공격모델 설계 1개로 만든 제안서다.
> ✅ **2026-09-11 사용자 채택: S2**(초기값 그대로). 구현 = migration 081 + `coupon-charge.ts` `spendLookupBudget`.
> 설계 정본: `docs/discount-coupon-design.md` §6·§11. 결정 B("로그인 계정이면 쿠폰 사용 가능")는 유지한다.

---

## 결론

**합산 상한은 계정 확인으로 만드는 게 아니다.** 계정 수와 상관없이 세는 **전역 카운터**(마이그레이션 081 한 개)만이
진짜 상한이 된다. 계정 확인은 "이 조회를 어느 예산 풀에서 차감하느냐"를 가르는 데 쓴다 — 그래야 공격자가 공용 풀을
태워도 정상 고객 전원이 막히는 DoS 가 되지 않는다.

**추천: S2 — 위조할 수 없는 신호 2개로 계정을 3등급으로 나누고 풀을 따로 둔다.**
이메일(open) 하루 20 · 소셜 로그인(social) 40 · 결제 이력(paid) 30회, 계정(또는 소셜 신원)당 하루 10회.
무료 계정 공격자가 하루에 수확할 수 있는 코드는 **0.2장**(발급이 고르게 퍼진 경우) ~ **1장**(한 등급에 몰린 경우)으로 줄어든다.
지금은 **무료 계정 수천 개로 하루 안에 전량**이다.

## 근거

### 1. 지금의 실제 비용 — 사실상 무제한 오라클

체크아웃 `?coupon=` 미리보기는 코드를 쓰지 않고도 "살아 있는 코드 + 할인율"을 알려 준다.
prepare 도 같은 오라클이다(`expectedAmount` 를 일부러 틀리게 보내면 적중=409 `amount_changed`, 빗나감=`not_found`).
두 입구 모두 `resolveChargeForUser` 의 **새 코드 분기 한 곳**을 지나므로 게이트도 거기 하나면 된다.

| 가정 | 값 |
|---|---|
| 코드 공간 | 등급 5개 × 4자리 = 50,000 (등급당 10,000) |
| 발급 | 500장, 무작위 |
| 적중률 d | 고르게 퍼지면 1% · 한 등급(50%)에 몰리면 5% |
| 현재 방어 | 계정당 하루 "없는 코드" 10회 |
| 계정 생성 비용 | **0원** — `signup/route.ts` 가 `email_confirm: true`, CAPTCHA·레이트리밋 없음 |

→ 전량 수확 = 빗나감 약 49,500회 ÷ 10 = **무료 계정 4,950개 · 하루**(한 등급 집중이면 약 950개).

### 2. 이 코드베이스에서 "믿을 수 있는" 계정 신호 — 절반이 위조 가능하다

| 신호 | 저장 위치 | 사용자가 위조? | 쓸 수 있나 |
|---|---|---|---|
| 소셜 신원 `user.identities[]` (kakao·google) | `auth.identities` (GoTrue 가 검증된 id_token 으로 씀) | **불가** | ✅ 강함 — 무료이면서 위조 불가인 유일한 사람 단위 키 |
| 실결제 이력 `payment_orders` fulfilled | service role 전용 테이블 | **불가** | ✅ 강함 — 돈이 드는 유일한 등급(최저 990원) |
| 로그인 공급자 `app_metadata.provider(s)` | GoTrue 가 씀 | 불가 | 🟡 등급 구분용(사람 수는 못 셈) |
| 🔴 `user_metadata.provider_id` → `kakaoUidHashFromUserMetadata` | `raw_user_meta_data` | **가능** — `supabase.auth.updateUser({data:{provider_id}})` 한 줄 | ❌ 절대 금지 |
| `email_confirmed_at` | signup 이 전원 true | 사실상 가능 | ❌ |
| `user_contact.phone` · readings · profiles | RLS 로 본인 insert/update | 가능 | ❌ |
| 계정 나이 `created_at` | GoTrue | 불가지만 미리 만들어 숙성 비용 0 | ❌ 게이트 불가 |
| 요청 IP | Vercel 이 `x-forwarded-for` 덮어씀 | 헤더는 불가, 프록시 회전은 싸다 | 🟡 보조만 |

⚠️ **"카카오 가입엔 휴대폰이 필요하다"(설계 §6-A 전제)는 확인되지 않았다.** 카카오 데브톡 공식 답변상 번호 없는 웹가입
카카오계정이 존재한다(https://devtalk.kakao.com/t/topic/140423). 소셜 등급을 "비싼 계정"으로 가정하면 안 되고,
"스크립트로 양산하기 번거로운 계정" 정도로 봐야 한다.

### 3. 방안 비교 (d = 1% / 5% 기준 하루 누설)

| 방안 | B 유지 | 무료 계정 공격자 누설 | DoS 로 막히는 사람 | 구현 |
|---|---|---|---|---|
| 현재 | ✅ | 사실상 무제한 | — | — |
| **S1** 단일 전역 풀(G=40) | ✅ | 0.4 / 2.0장 | **전원** — 무료 계정 4개로 몇 초 만에 | XS |
| **S2** 등급별 풀 ⭐ | ✅ | **0.2 / 1.0장** | 결제 이력 없는 이메일 가입자만 | S (~200줄 + SQL 1회) |
| **S3** S2 + 휴대폰 문자 step-up | ✅ | S2 와 같음 | 막힌 고객에게 30초 우회로 | M (~400줄 + 법률 검토) |
| **S4** 카카오/휴대폰 신원 필수 | ❌ **B 변경** | 0 (오라클 소멸) | 이메일 가입자 영구 제외 | M |

S2 에 공격자가 소셜 신원 4개(매일 재사용)를 준비하면 0.6 / 3.0장, 결제 계정 3개(990원 × 3)까지 쓰면 0.9 / 4.5장/일.
그래도 500장 전량까지 111일 이상이고, **풀이 소진되는 순간 매일 알림이 가므로** 사람이 배치를 끊을 수 있다.

## 실행 단계 (S2 채택 시)

1. **결정**: 풀 초기값 open 20 / social 40 / paid 30(KST 하루, production·test 따로), 주체당 10. 전단 대량 배포일 전엔 2배.
2. **migration 081** `rate_counters(bucket, period_key, used_count)` + 원자 RPC `consume_rate_counter`(초과면 null 반환).
   RLS on·정책 없음·public/anon/authenticated 실행권 회수. 앱보다 **먼저** 수동 적용(080 다음).
   - 056 `membership_benefit_usage` 는 못 쓴다: `user_id` 가 `auth.users` FK(on delete cascade)라 전역 버킷을 담을 수 없다.
3. **`resolveChargeForUser` 새 코드 분기**에서 조회 **전에** 두 번 선차감: 주체 버킷 → 등급 풀. **적중도 센다**
   (동시 폭주로 상한을 넘지 않게, 이미 아는 코드 태우기도 풀로 묶이게). RPC 오류·null 이면 거부(실패-닫힘).
   두 거부 모두 조회 전이라 코드 유효 여부와 무관하게 같은 응답 — 오라클이 다시 열리지 않는다.
4. **등급 판정** `lookupTier`: 익명(`is_anonymous`) → 조회 안 함 · paid(fulfilled, amount>0, `origin.env='production'`
   또는 2026-08-29 이전 주문) · social(`user.identities[]` 에 kakao/google, 키=sha256(provider:id) — 탈퇴·재가입해도 같은 키) · 나머지 open.
   🔴 `user_metadata`·`email_confirmed_at`·`user_contact.phone` 을 쓰지 않도록 테스트로 고정.
5. `resolveChargeForUser` 두 번째 인자를 `userId` → `user` 객체로. prepare·체크아웃이 **같은 `getUser()` 결과**로 등급을 내야 한다
   (한쪽만 바뀌면 화면·청구 불일치 409).
6. 새 사유 `busy`("지금은 쿠폰 확인이 몰려 잠시 멈췄어요. 내일 0시에 다시 열립니다. 등록된 쿠폰·결제는 그대로") —
   `rate_limited` 와 분리. 풀이 50%·100% 에 닿으면 `sendOpsAlertEmail`(기존) 1회씩.
7. 가드 테스트: RPC null → 조회 0회 · RPC 오류 → 거부 · 동시 N 요청에서 풀 초과 0 · 위조 `user_metadata` 로 승급 불가 ·
   test/production 버킷 분리 · refunded·staging 주문은 paid 아님.
8. 순서: **PR6(발급 화면)보다 먼저.** 발급 전이면 오라클은 비어 있다. PR5(입력 UI)는 미리보기를 POST(서버 액션)로 설계 — S3 를 붙일 자리.

운영 규칙: 알림이 오면 — 정상 급증이면 노브를 올려 재배포하거나 그날 풀 행을 지워 리필, 공격이면 그 배치를 `disabled_at` 으로
끄고 재발행(080 덕에 정상 고객은 재발행 코드를 쓸 수 있다). social 풀이 3일 연속 소진되면 S3 착수.

## 대안 (채택하지 않은 것)

- **S1 단일 전역 풀** — 상한은 가장 작지만 무료 계정 4개로 KST 0시에 전 고객을 막을 수 있다. 공격자와 정상 고객을 가를 수단이 없다.
- **S3 휴대폰 문자 step-up** — S2 풀이 소진돼 `busy` 를 받은 사람에게만 "문자로 번호 확인하면 바로 사용"을 띄운다(필수 아님 → B 유지).
  Solapi 연동 재사용, SMS 약 18원/건(⚠️ 8원 표기도 있어 검증필요), 발송 상한 필수(SMS 펌핑), '본인인증' 표현 금지(번호 점유 확인일 뿐, ⚠️ 법률 검토).
  공격이 실제로 관측되면 붙인다.
- **S4 신원 필수** — B 를 뒤집는다. S2 에서 open 풀이 이미 하루 20회라 추가로 줄여 주는 누설은 0.2 / 1.0장뿐 — 얻는 것에 비해 퍼널·결정 비용이 크다.
- **이메일 인증 켜기** — `/api/auth/confirm-email` 이 인증 없이 아무 계정이나 강제 확인해 무력하고, 일회용 메일이면 공격 비용 약 0원. 결제 직전에 메일함 왕복만 끼어 전환이 깎인다.
- **가입 단계 CAPTCHA** — 계정 생성 경로가 셋이다(`admin.createUser` 는 캡차 우회 · 공개 GoTrue `/signup` 은 anon 키로 직접 호출 · 카카오/구글 첫 로그인은 면제). 게이트는 쿠폰 분기 한 곳이 완결된다.
- **Turnstile·BotID 단독** — 상한을 못 만든다. 풀이 서비스가 건당 약 2원(⚠️)이면 뚫린다. S3 의 차선으로만.
- **IP 버킷 주 방어** — 통신사 CGNAT 오탐, 주거용 프록시로 우회. 알림 분석에서 한 출처 쏠림이 보이면 같은 RPC 에 HMAC(IP) 버킷 5줄로 추가.
- **Vercel WAF 레이트리밋** — 창이 최대 10분이라 하루 상한이 안 되고, 규칙이 git 밖에 남는다.
- **PASS·통신사 본인확인(CI)** — B 변경 + 사업자 계약·건당 비용. 이 손실 규모엔 과하다.
- **"없는 코드만" 세는 전역 카운터**(지금 계정당 방식 확장) — 읽고 나서 차감하는 사이 동시 폭주로 상한을 넘기고, 태우기를 못 묶는다.

## 가정이 무너지는 조건

| 조건 | 결과 | 대응 |
|---|---|---|
| 전단 배포일 정상 조회가 풀에 닿음(체크아웃 1~5명/일 가정 붕괴) | 평시에도 `busy` | 50% 알림 보고 노브 상향 |
| 카카오·구글 계정을 사실상 0원에 양산 | social 풀 매일 소진 → 전단 신규 고객 다수 막힘 | S3 |
| 공격자가 실결제(990원 × N)를 감수 | paid 풀 소진 | 카드 추적 + 배치 회수 |
| 한 등급에 수천 장 발급(d 증가) | 누설이 d 에 정비례 | 근본책은 6자리 영숫자(§11-A) — **인쇄 전이 마지막 시점** |
| 순차 발급 | 이웃 번호 추측 → d 계산 무의미 | 무작위 발급 필수 |
| 인쇄물·사진 유출 | 계정 확인 무관 | `disabled_at` 배치 회수뿐 |
| `getUser()` 를 `getClaims()` 로 교체 | `identities` 가 사라져 전원 open 강등(안전 쪽 실패, DoS 노출 증가) | 주석·테스트로 고정 |
| staging 샌드박스 결제가 `origin=production` 으로 찍힘 | paid 등급 위조 | ⚠️ 검증필요 |
| 대시보드에서 익명 로그인 켬 | 익명 계정이 open 풀로 | `is_anonymous` 가드 |

## ⚠️ 검증필요 (코드·공개 문서로 확정 못 한 것 — 프로덕션 DB·대시보드 접근 금지로 조사)

- 프로덕션에 이미 발급된 쿠폰이 있는지(없다면 지금 오라클은 비어 있다)
- `getUser()` 의 `user.identities[].id` 가 카카오 회원번호·구글 sub 인지 — 테스트 계정으로 확인
- `consume_rate_counter` 의 `ON CONFLICT DO UPDATE ... WHERE` 불충족 시 NULL 반환·동시성 — 로컬 Supabase 가 없어 첫 적용이 곧 프로덕션
- 카카오·구글 계정 생성에 휴대폰이 필요한지(social 등급의 실제 비용)
- Supabase 대시보드: 공개 가입 허용 · Confirm email · 익명 로그인 · 수동 링크 설정, `admin.createUser` 의 IP 레이트리밋 유무
- staging 의 `NICEPAY_MODE`, Vercel Host 라우팅 가정(paid 필터의 전제)
- 체크아웃 도달 수 재실측 · 전단 고객의 가입 경로 비율 · 고객당 실제 조회 횟수(RSC 재렌더·prefetch)
- `rate_counters` 에 쌓이는 가명 식별자가 처리방침의 '부정이용 방지' 목적에 포함되는지

## 🔴 별건 보안 발견 (쿠폰 범위 밖 — 따로 다뤄야 함)

1. **`/api/auth/confirm-email` 무인증 강제 확인** (`src/app/api/auth/confirm-email/route.ts`)
   - 로그인 없이 이메일 주소만 받아 그 계정을 "이메일 확인됨"으로 바꾼다(코드로 확인).
   - 가입 여부가 404/200 으로 갈려 **이메일 열거 오라클**, 요청 1회에 `listUsers` 최대 20페이지 순회로 **증폭 공격** 가능.
   - ⚠️ 검증필요·잠재 심각: 공격자가 `victim@gmail.com` 으로 먼저 이메일 가입하면(signup 이 전원 자동 확인) "확인된 이메일" 계정이 생기고,
     피해자가 나중에 구글로 로그인할 때 Supabase 자동 연결로 **공격자 계정에 붙을 수 있다**(선점 가입 탈취 —
     https://supabase.com/docs/guides/auth/auth-identity-linking). 테스트 계정 두 개로 재현 확인이 먼저다.
2. **076 탈퇴 원장이 위조 가능한 `user_metadata` 를 쓴다** — 탈퇴 직전 `provider_id` 를 덮어쓰면 무료 하루 1회 스냅샷을 우회한다
   (`src/app/api/account/delete/route.ts`, `src/lib/kakao/uid-hash.ts`). 같은 값을 `user.identities[]` 에서 읽으면 위조 불가.
3. **`getMemberBenefitUsed` 주석·코드 불일치** — 주석은 "오류 시 limit 으로 간주", 코드는 0(실패-열림). 쿠폰은 #807 에서 실패-닫힘으로 분리했다.
4. **`policies.ts` `hashIp` 가 소금 없는 SHA-256** — IPv4 는 역산된다. "원문 IP 복구 불가" 주석은 사실이 아니다.
