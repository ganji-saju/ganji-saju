# Claude Code · Codex 상호 검토

이 프로젝트에서 두 도구의 **실제 제안과 결과물**을 같은 기준으로 비교한다. 도구 이름만으로 우열을 정하지 않는다. 이 문서는 공유 파일을 통한 비동기 협업 절차이며, 다른 도구의 세션을 자동 실행하거나 대화를 실시간 연결하는 기능은 아니다.

## 시작과 전달

- 사용자가 비교·토론을 요청하면 이 폴더의 해당 주제 `request.md`와 상대 의견을 먼저 읽는다. 관련 주제가 없으면 `YYYY-MM-DD-주제/`를 만들고 요청을 기록한다.
- 요청에는 사용자 목표, 비교할 A/B의 커밋·파일·제안, 기준 커밋, 제약, 검증 방법을 적는다. 후보가 하나뿐이면 상대의 대안을 기다리며 승자를 정하지 않는다. 작성 도구를 확인하지 못한 코드는 임의로 Claude/Codex 작업이라고 분류하지 않는다.
- 각 도구는 자기 파일만 작성한다: `codex-r1.md`, `claude-r1.md`, 이후 `codex-r2.md`, `claude-r2.md`. 동시 작업 시 상대 파일을 수정하거나 대신 작성하지 않는다. `request.md`의 범위를 바꾸려면 자기 의견에서 변경안을 제시한다.
- 같은 체크아웃에서는 파일로 바로 전달한다. 다른 워크트리에서는 해당 **동일 저장소**의 브랜치와 커밋을 공유하고 fetch 후 읽는다. 미커밋 파일이 다른 워크트리에 보인다고 가정하지 않는다. 다른 프로젝트나 Harness 메모리는 조회하지 않는다.

## 비교와 토론

1. **1차 의견:** 본인 추천안, 상대안의 장점, 구체적인 문제, 증거, 미확인 사항, 상대에게 묻는 질문을 적는다. 근거는 파일/행·커밋·실행 명령과 종료 결과·가상 사례로 연결한다. 개인 정보와 비밀값은 넣지 않는다.
2. **2차 의견:** 실제 상대 파일을 읽은 다음, 반론별로 수용/기각/검증 필요를 구분하고 이유를 적는다. 의견이 바뀌면 무엇 때문에 바뀌었는지 밝힌다. 상대 답변이 없으면 `상대 응답 대기`이며 토론 완료나 합의를 주장하지 않는다.
3. **결론:** 두 의견을 읽은 도구가 `decision.md`에 두 안의 정확한 버전, 기준별 비교, 채택안 또는 혼합안, 남은 이견, 검증 결과를 작성한다. 상대의 명시적 동의가 없으면 `작성 도구의 권고`로 표기한다. 합의는 양쪽 파일에서 확인된 항목에만 사용한다.
4. 기본 두 차례로 마친다. 결론이 나지 않으면 실제 차이를 확인할 최소 실험 또는 사용자의 선택이 필요한 쟁점을 제시한다. 서로의 응답을 기다리며 무한 대기하거나 자동 호출을 반복하지 않는다.

## 공통 판단 기준

| 기준 | 확인할 증거 |
|---|---|
| 사용자 목표 충족 | 요청한 동작·화면·콘텐츠가 실제로 제공되는가 |
| 정확성 | 계산·명리 근거와 해석이 연결되는가, 없는 사실을 만들지 않는가 |
| 이해하기 쉬움 | 처음 읽는 사람이 뜻과 활용 방법을 설명할 수 있는가 |
| 구체성·중복 | 개인별 확인된 조건을 반영하며 같은 말을 반복하지 않는가 |
| 안정성·보안 | 오류·누락·권한 경계·PDF 넘침 등을 검증했는가 |
| 비용·속도·유지보수 | 측정값이 있는가, 추가 복잡성이 필요한가 |

임의 점수나 미측정 개선율은 만들지 않는다. 테스트 통과가 해석의 적중도·공감도·매출 개선을 증명한다고 쓰지 않는다. 문서상의 지시 변경과 실제 생성 결과 검증을 구별한다.

## 사용자에게 답하는 형식

추천 결과 → 두 안의 장단점과 증거 → 상대 반론과 반영 여부 → 확인되지 않은 점 순서로 짧게 답한다. 상대 의견을 실제로 받았는지 명시한다. 비교·토론 요청만으로 제품 변경이나 운영 배포를 실행하지 않는다. 구현·머지·배포는 사용자가 승인한 범위와 AGENTS.md 절차를 따른다.

## 의견 파일 양식

- 작성 도구 / 날짜 / 읽은 상대 파일과 커밋:
- 내 추천과 근거:
- 상대안에서 유지할 장점:
- 반론 및 수용·기각·검증 필요:
- 실제 실행한 검증과 결과:
- 미확인 사항 / 상대에게 묻는 질문:
- 상태: 1차 의견 / 상대 응답 대기 / 2차 의견 / 작성 도구의 권고 / 확인된 합의
