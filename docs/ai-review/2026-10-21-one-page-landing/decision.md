# 결정 — 한 장짜리 랜딩 + 비회원 주문 (2026-10-21)

> 2회 검토로 종료. Codex 2차 판정은 "보류"였고 그 뒤 반영분은 Codex 재검토를 받지 않았다 → 아래는 **작성 도구(Claude)의 권고**다. 합의가 아니다.

## 2차 지적 반영 (모두 실패하는 테스트 먼저)
- 발송·다시 만들기 DB 갱신에 풀이 id 조건(확인 직후 바뀐 풀이 발송·동시 생성 덮어쓰기 방지)
- 관리자 "결제 확인" 뒤 주문이 실제 paid 인지 다시 확인(원장이 처리 중이면 409)
- GA 식별자는 명시 동의(granted)일 때만
- Vercel Analytics·Speed Insights 로 가는 `/r/<토큰>` 주소를 가림(beforeSend)
- 발송 실패 응답에서도 관리자 화면 새로고침 → "다시 보내기" 노출
- 첫 발송 1년 지난 링크는 다시 보내지 않음
- 보관 기간 삭제의 마지막 갱신에도 같은 만료 조건(조회 뒤 새로 발송된 주문 보호)
- 이름 규칙 완화(하이픈·아포스트로피 허용, 링크·숫자는 계속 거부)
- 나이스 승인 뒤 확정 전 단계 실패 시 승인 거래번호(tid)를 운영 경보에 남김

## 남은 이견·위험 (사용자 판단 필요)
1. **정산 크론이 나이스페이를 조회하지 않음(기존 결함, 전 상품 공통).** Codex 는 출시 조건이라 봄. 작성 도구 판단: 랜딩 주문은 경보 + 관리자 "결제 확인" + tid 경보로 사람이 복구 가능하므로 이 PR 은 진행하고, 나이스 정산은 별도 PR 로 **광고비를 크게 쓰기 전에** 처리 권고.
2. **nicepay return 라우트 분기의 라우트 단위 테스트 없음**(헬퍼 테스트만). Codex 반대.
3. 다시 만들기·저장 실패 때 이전 원본 삭제가 실패하면 고아 원본이 남을 수 있음(오류를 삼킴) — 경미.
4. 발송 상태를 잡은 직후 환불이 겹치면 닫힌 링크 문자가 나갈 수 있음 — 경미.
5. 이메일 필수(설계대로) — 고령 손님 장벽, 제품 결정.
6. 생성 잠금은 인스턴스 메모리 — 동시 생성 시 한쪽은 409 로 끝나지만 AI 비용은 두 번.

## 머지 전 리뷰(pr-reviewer, 새 컨텍스트) 반영 — 2026-10-21
- [필수] 일반 결제 준비(/api/payments/prepare)가 랜딩 상품을 막지 않던 문제 → 410 차단(로그인 사용자가 직접 부르면 랜딩 주문 행 없이 돈만 받던 경로)
- 결제 원장을 먼저 확정하고 랜딩 주문을 paid 로(원장 실패 시 주문은 결제 대기 → '결제 확인'으로 둘 다 복구), '결제 확인'이 랜딩 주문을 직접 맞춤
- 전달 안 한 거래(주문 취소·없음)는 GA 구매로 보내지 않음
- 같은 번호 하루 제한에서 결제창을 닫은 카드 시도 제외, 조회 실패 시 통과시키지 않음(fail-closed)
- 관리자 라우트 UUID 아닌 id → 404, 횟수 제한 Map 정리
- **결과 토큰을 페이지 주소에서 제거**: `/r/<토큰>` 은 httpOnly 쿠키로 옮기고 `/r/view` 로 보냄 → GTM·픽셀 등 페이지 스크립트가 토큰을 읽을 수 없음
- **DB 제약**: payment_orders 의 user 빈값은 랜딩 상품 두 개에만 허용(091 에 추가)
- 미반영(후속): 무통장 접수 문자 악용 방지 강화(캡차·입금 뒤 발송) — 광고비 쓰기 전 권고 · hasSameOrigin 3중 복사 정리
