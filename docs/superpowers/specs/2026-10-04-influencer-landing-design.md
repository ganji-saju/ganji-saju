# 인플루언서 전용 신년운세 랜딩 — 설계서

- 작성: Claude Code, 2026-10-04 · 상태: **사용자 검토 대기**
- 사용자 결정: 방법 ①(랜딩만 별도 도메인, 결제는 간지사주) · 정가 32,000원 / 인플루언서 할인 40% → 19,200원 / 수수료 30%

## 1. 목적과 성공 기준

- 목적: 인플루언서 협찬으로 2027 신년운세를 판다. 손님에게는 간지사주와 별개인 신년운세 전용 브랜드처럼 보인다.
- 성공 기준
  1. 인플루언서마다 고유 주소(`새도메인/코드`)가 있고, 그 주소로 온 손님은 19,200원에 산다.
  2. 랜딩 표시 금액 = 결제 화면 금액 = PG 청구액(19,200원).
  3. 관리자가 인플루언서별 방문·판매·환불·수수료(결제액의 30%, 환불 건 제외)를 본다.
  4. 간지사주 메뉴·검색·가격표에는 이 상품이 나오지 않는다.

## 2. 사용자 결정과 ⚠️ 위험 (기록)

| 항목 | 결정 | 위험 |
|---|---|---|
| 정가 32,000원 표시 | 사용자 결정(2026-10-04) | ⚠️ 같은 풀이가 간지사주에서 19,900원에 공개 판매 중 — 판매 이력 없는 정가는 표시광고법상 부당한 할인 표시로 볼 여지. 법률 확인 권장. 완화책: 파트너판 구성 차별화 또는 32,000원 일반 판매 기간 |
| 결제창 상호 | 간지사주(푸꼬컴퍼니) 그대로 | 손님이 모르는 상호로 보고 취소·이의 제기 가능 → 랜딩·결제 화면에 "결제·풀이 제공: 간지사주(푸꼬컴퍼니)" 사전 안내 |
| 사업자 정보 | 랜딩 하단에 간지사주와 같은 사업자 정보 | 전자상거래법 표시 의무 |
| 인플루언서 광고 표시 | 인플루언서에게 "광고/협찬" 표기 안내 | 추천·보증 심사지침 |
| 수수료 지급 세금 | 사업자/개인별 원천징수 | ⚠️ 세무 확인 필요(이번 범위는 금액 집계까지) |

마진(건당, 참고): 19,200 − 수수료 5,760 = 13,440원에서 부가세·PG 수수료·AI 비용 차감 전. ⚠️ PG 수수료율 미확인.

## 3. 구성 요소

### 3-1. 파트너판 상품
- 결제 카탈로그(`src/lib/payments/catalog.ts`)에 `taste_new_year_2027_partner` 추가: 정가 32,000원, `requiresSlug`, 지급 이용권은 기존 신년운세와 **같은 이용권**(신년운세 화면·PDF·재열람이 그대로 동작해야 함).
- 숨김: 간지사주의 메뉴·가격표(`getPriceDisplayMap` 소비처)·검색·사이트맵에 노출하지 않음. 재결제 차단(사주 정체성 + 신년운세)은 기존 신년운세와 공유 — 이미 산 사주는 다시 못 산다.
- 멤버십 50% 할인은 적용하지 않음(`MEMBER_DISCOUNT_PERCENT_BY_PACKAGE`에 넣지 않음).

### 3-2. 인플루언서(파트너) 정보 — 새 테이블 (마이그레이션 090)
- `partners`: `code`(주소용, 영문·숫자 3~20자, 유일) · `name` · `discount_percent`(기본 40) · `commission_percent`(기본 30) · `active` · `created_at`. RLS 활성·정책 없음(service 전용).
- `partner_visits`: `partner_code` · `visited_on`(KST 날짜) · `count` — 랜딩 방문 일별 집계(개인정보 없음). 봇 필터는 기존 방문 지표 규칙 재사용.
- 새 SECURITY DEFINER 함수를 만들면 같은 마이그레이션에서 anon EXECUTE 회수.

### 3-3. 랜딩 페이지 (새 도메인)
- 같은 Next.js 앱에서 `src/proxy.ts`가 **호스트가 새 도메인일 때** 경로를 `/partner-landing/[code]`로 내부 전환. 새 도메인에서는 간지사주의 다른 경로를 열지 않는다(랜딩·정책 문서·정적 자원만).
- 화면: 새 브랜드 디자인 한 장 — 신년운세 소개 · "32,000원 → 19,200원(40%)" · 구매 버튼 · 하단 사업자 정보와 "결제·풀이 제공: 간지사주(푸꼬컴퍼니)".
- 없는 코드·비활성 코드: "지금은 이용할 수 없는 링크입니다" 안내만 보이고 **구매 버튼은 숨긴다**(정가 32,000원 결제로 이어지지 않게).
- 방문 집계: 페이지 요청 시 `partner_visits` +1(서버, 실패해도 화면은 정상).

### 3-4. 랜딩 → 결제 연결
- 구매 버튼 = `ganjisaju.kr/membership/checkout?product=new-year-partner&partner=코드`. 사주 입력이 필요하면 기존 신년운세 흐름(사주 입력 → 결제)을 따른다 — 구현 계획에서 경로 확인.
- 체크아웃은 `partner` 값을 짧은 쿠키(체크아웃 경로, 30분+로그인 왕복 유지)에 두고, 금액 계산은 기존 공용 코드와 같은 자리(`resolveChargeForUser`)에서 파트너 할인으로 낸다 → 화면 금액 = prepare 금액 = `order.amount`.
- 로그인 전에도 19,200원 표시(공용 코드와 같은 이유 — 추측 위험 없음, 실제 청구는 로그인 뒤 같은 계산).
- 주문 기록: `payment_orders.metadata.partnerCode`, `metadata.partnerCommissionPercent`(주문 시점 스냅샷). `coupon_code`는 비움(승인 직전 쿠폰 검사 회피 — 공용 코드와 동일).
- 쿠폰·공용 코드·멤버십과 겹치지 않음. 파트너 상품에는 파트너 할인만.

### 3-5. 관리자 화면
- `/admin/partners`(super_admin): 파트너 등록·수정(이름·코드·할인율·수수료율·활성) · 각 파트너 주소 복사.
- 실적(달력 기간, 기존 `metric-periods` 규칙): 방문 수 · 결제 건수·금액 · 환불 건수·금액 · 수수료 = Σ(정상 결제 `order.amount` × 스냅샷 수수료율) − 환불 건. 부분 환불은 남은 금액 기준.
- 정산은 수동(화면 숫자를 보고 지급). 구매자 개인정보는 보여 주지 않는다.

## 4. 범위 밖 (다음 단계)

- 인플루언서 본인 로그인·전용 화면 · 자동 정산·지급 · 파트너판 구성 차별화 · 여러 상품 확장.

## 5. 오류·경계

- 쿠키가 없거나 코드가 비활성: 파트너 상품을 정가 32,000원으로 청구하지 않도록 **결제 화면에서 할인 미적용 사유 표시 + prepare 에서 표시 금액 대조(기존 expectedAmount 가드)**.
- 할인율·수수료율 변경: 이미 만든 주문은 스냅샷 유지, 새 주문부터 반영.
- 환불: 기존 환불 경로 그대로(`order.amount` 기준). 수수료 집계에서 환불 건 차감.

## 6. 검증

- 단위: 파트너 할인 계산(32,000 → 19,200) · 화면 금액 = 주문 금액 · 쿠폰 검사 미통과(coupon_code 비움) · 비활성 코드 · 수수료 집계(부분·전체 환불).
- 가드: 결제 원장 초크포인트 테스트(`coupon-chokepoint.test.ts`) 목록 갱신 · 간지사주 가격표·사이트맵에 파트너 상품 없음.
- 실화면: staging 에서 새 도메인(또는 임시 서브도메인) 랜딩 → 체크아웃 19,200원 → 결제창 금액 확인(사용자).
