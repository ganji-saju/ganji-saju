# 한 장짜리 랜딩 + 비회원 주문(종합사주·2027 신년운세 PDF) 설계서

- 작성: 2026-10-21 (Claude Code)
- 근거: 대표 수정 요청서 `간지사주 수정 요청 20261020.pptx`(14장) + 사용자 답변(2026-10-21)
- 상태: 사용자 승인 대기

## 1. 왜 하는가

- 하루 평균 80명 이상 들어오지만, 무료 풀이도 안 보고 아무 행동 없이 나간다. 대표 판단: 무엇을 봐야 할지 모르겠고 어렵기 때문이다.
- 들어오는 손님은 대부분 50대 이상 여성이다.
- 같은 나이대를 노리는 경쟁 업체는 모두 같은 구조의 한 장짜리 랜딩을 쓴다.
  - 순서: 사주를 봐야 하는 이유 → 기대감 → 후기 → 상담사 검증 → 결제
  - 상품: 종합사주 하나, 또는 종합사주와 신년운세 둘
- 성공 기준: 처음 온 손님이 화면 하나에서 상품을 고르고, 로그인 없이 결제나 입금 신청까지 끝낸다. 관리자는 주문마다 PDF를 만들고 확인한 뒤 손님에게 보낸다.

## 2. 하는 것 / 안 하는 것 / 하면 실패인 것

**하는 것**
- 한 장짜리 랜딩 페이지
- 상품 2개
  - 종합사주 1인: 29,900원 (정가 60,000원 취소선)
  - 2027 신년운세: 19,900원 (정가 40,000원 취소선)
- 비회원 주문서. 결제 수단은 둘이다.
  - 카드·간편결제: 기존 나이스페이
  - 무통장 입금: 관리자가 입금을 확인하는 방식
- 관리자 주문 화면. 흐름: 입금 확인 → 풀이 생성(기존 외부 주문 PDF 생성기) → 상담사 확인 → 발송
- 손님 결과 링크. 문자·이메일로 보내고, 링크에서 보기와 PDF로 저장이 된다.

**안 하는 것**
- 기존 기능 삭제. 오늘운세·궁합·멤버십·보관함·결제내역은 주소로 계속 열린다. 기존 결제 손님이 산 풀이도 그대로다.
- 랜딩 상품을 회원 이용권과 묶기. 랜딩 주문은 회원 계정·보관함과 연결하지 않는다.
- 파트너스. 별도 설계로 하고, 이 랜딩의 상품 2개를 파트너 판매 대상으로 쓸 수 있게 주문에 유입 출처 칸만 남긴다.
- 자동 발송. 반드시 상담사가 확인한 뒤 보낸다.

**하면 실패인 것**
- 지어낸 후기, "실시간 접수 현황" 같은 가짜 활동 표시
- 사실이 아닌 사람·자격 표시
- 결제는 됐는데 주문이 사라지거나 풀이가 발송되지 않는 것
- 남의 주문이나 결과를 볼 수 있는 링크
- 기존 결제자가 산 풀이를 못 보게 되는 것

## 3. 사용자가 정한 것 (그대로 따른다)

| 항목 | 결정 | 비고 |
|---|---|---|
| 결제 | 간지사주 카드결제 랜딩 + 무통장 입금도 함께 | PPT 3번 장의 두 안을 합침 |
| 정가 표시 | 60,000원·40,000원 취소선 유지 | ⚠️ 그 가격에 판 근거가 없으면 표시광고법상 허위 할인 소지. 사용자에게 고지했고 사용자가 결정함(신년운세 앱 상품은 19,900원에 공개 판매 중). |
| 풀이 확인 | 상담사가 확인한 뒤 발송 | 광고 문구를 이 사실에 맞춘다 |
| 후기 | 실제 후기를 사용자가 보내 줌 | 받기 전까지 후기 칸은 숨긴다 |
| 결과물 | 관리자 외부 주문 PDF와 같은 내용 | 종합 = `lifetime`, 신년운세 = `new-year` |
| 화면 순서·문구 | PPT 4~14장 | 아래 §5 |
| 상담사 | 대표 본인. 보유 자격 5종은 대표 기준. 기존 최고 관리자 계정으로 미리보기 → 발송 또는 다시 만들기. 문장 수정 기능 없음 | 새 권한·편집 화면 불필요 |
| 사진 | PPT 4·7·11장의 사진을 그대로 사용 | ⚠️ AI로 만든 그림으로 보이고(한자·기관 이름 깨짐) 화면 한자 금지 규칙과도 걸리지만, 사용자 결정으로 사용. 작성자 판단으로 사람 사진에 이름·직함을 붙이지 않고, 사진 아래에 "이미지는 연출 사진입니다"를 작게 넣는다. |
| "이번 달 특별 할인가" | 유지 | ⚠️ 기한 없는 상시 할인 표시 위험을 고지했고 사용자가 결정함 |
| 무통장 계좌 | 사용자가 Vercel 환경변수로 직접 입력 | 비어 있으면 무통장 선택지를 숨김 |

## 4. 화면 흐름

1. 손님이 랜딩에 들어와 내려 읽는다. 아래에 붙은 "풀이 신청하기" 버튼은 계속 따라다닌다.
2. 상품 카드에서 상품을 고르면 주문서로 내려간다.
3. 주문서에 입력한다.
   - 필수: 상품, 이름, 성별, 생년월일(양력·음력·윤달), 태어난 시간(모름 가능), 휴대폰, 이메일
   - 선택: 남기실 말
   - 결제 수단: 카드·간편결제 / 무통장 입금
   - 동의: 개인정보 수집·이용, 이용약관·환불 기준
4. 카드를 고르면 나이스페이 결제창 → 결제 완료 화면("영업일 1~2일 안에 문자·이메일로 보내 드립니다") → 접수 확인 문자.
5. 무통장 입금을 고르면 입금 안내 화면(은행·계좌·예금주·금액·입금자명=주문자 이름·입금 기한) → 같은 내용의 문자.
6. 관리자는 주문 목록에서 확인한다.
   - 무통장 주문은 "입금 확인"을 누른다.
   - 결제가 된 주문은 "풀이 만들기"를 누른다. 기존 생성기를 쓰고 1~4분 걸린다.
   - 미리보기로 내용을 확인한 뒤 "확인 완료·발송"을 누른다.
7. 손님은 문자·이메일로 결과 링크를 받는다. 링크를 열면 풀이 화면과 "PDF로 저장" 버튼이 있다.

## 5. 랜딩 구성 (PPT 장 번호)

| # | 칸 | 내용 |
|---|---|---|
| 1 | 첫 화면 (4장) | "내가 앞일을 미리 알고 준비한다면…" 질문 2줄 + "2,000년 넘게 이어져 온 사주풀이, 사람들은 왜 지금도 사주를 볼까요?" + 신청 버튼 |
| 2 | 사주를 보는 이유 (5장) | 원문 그대로 |
| 3 | 사주란 (6장) | 원문 그대로. "정해진 운명을 단정하는 도구가 아니라" 문구 유지 |
| 4 | 간지사주 소개 (7장) | 원문 그대로 |
| 5 | 상품 고르기 (8·9장) | 카드 2장. 가격·정가 취소선·쪽수·목차 이미지·풀이 예시 이미지·"이 상품 선택" 버튼 |
| 6 | 가격 안내 (10장) | "가격이 부담되신다면, 하나만 먼저…" 문구. "이번 달 특별 할인가"는 정가 결정과 묶여 같은 위험이 있어 §9에서 확인 |
| 7 | 상담사 소개 (11장) | 소개 글 + 보유 자격 5종 이름 + 실제 자격증 사진 |
| 8 | 이런 분께 추천 (12장) | 6가지 + 마무리 문장 |
| 9 | 후기 | 사용자가 보낸 실제 후기. 이름 가운데 글자 가림, 원문 그대로, 별점은 받은 경우만 |
| 10 | 주문서 (13장) | §4-3 |
| 11 | 이용 안내·자주 묻는 질문·면책·사업자 정보 (14장) | 아래 문구 수정 반영 |

**PPT 문구 중 사실에 맞춰 고치는 곳**
- 11장 "전문가들이 정성을 다해 풀이하며" → "자격을 갖춘 상담사가 풀이를 직접 확인해 보내 드립니다." 사실과 다른 "직접 풀이"는 쓰지 않는다.
- 14장 자주 묻는 질문 "카드, 간편결제, 계좌이체를 지원합니다" → "카드·간편결제와 무통장 입금을 지원합니다." 나이스페이 계좌이체는 영구 제외 상태다.
- 8장 "사주풀이 페이지 ~80장 이상" → 실측 최소 74쪽(`docs/admin-external-report.md`)이라 "70쪽 이상". 9장 신년운세 "~30장 이상"은 구현 때 실측해 그 최소값으로 쓴다.
- 14장 환불: 카드는 결과 발송 전 전액 취소, 무통장은 발송 전 계좌로 반환. 발송 뒤 기준은 기존 `/refund-policy`의 디지털 콘텐츠 기준을 따른다.

**50대 이상 손님을 위한 화면 기준**
- 본문 18px 이상, 버튼 높이 56px 이상, 글자 대비 4.5:1 이상
- 한 줄에 한 가지 입력, 생년월일은 큰 선택 상자
- 390px 폭에서 가로 넘침이 없어야 한다
- **한자는 쓰지 않는다**(프로젝트 규칙). 태어난 시간 선택지는 "자시(밤 11:30~새벽 1:29)"처럼 한글과 시간만 쓴다.

## 6. 구현 방향 (빌더가 따를 것)

### 6-1. 위치
- 새 경로 `/saju-report`에 먼저 만든다. staging에서 대표가 확인한 뒤 `/`를 이 랜딩으로 바꾸는 것은 **별도 단계**로 한다.
- 비주얼 변경은 운영 반영 전에 별도로 확인받는다는 프로젝트 규칙 때문이다.
- `/`를 바꾼 뒤 기존 홈은 `/home`으로 옮긴다. 기존 머리글 메뉴는 그대로 두고, 랜딩에는 랜딩 전용 간단한 머리글을 쓴다. (빌더 판단)

### 6-2. 데이터 (마이그레이션 1개, 운영 적용은 사용자 승인 후 수동)
- 새 테이블 `report_orders` (service 전용, RLS 켜고 정책 없음 — 기존 결제 테이블과 같은 방식)
  - `id`, `order_no`(사람이 읽는 번호)
  - `product`: `lifetime` | `new-year`
  - `amount`, `pay_method`: `card` | `bank`
  - `status`: `awaiting_deposit` → `paid` → `generated` → `sent`, 그 밖에 `cancelled`·`refunded`
  - 주문자 정보: `name`, `phone`, `email`, `birth_input` jsonb(외부 주문 PDF 입력과 같은 형식), `memo`
  - 결제 연결: `payment_order_id`(카드만), `external_report_id`(생성 후)
  - 결과 링크: `result_token`(추측 불가, 32바이트 이상 난수)
  - 기록: `deposit_confirmed_at`/`by`, `reviewed_at`/`by`, `sent_at`, `source`(유입 출처·파트너 대비), `created_at`
- 카드 결제는 기존 `payment_orders`에 같이 기록해 결제 흐름·환불·대시보드 매출을 그대로 쓴다.
  - 이를 위해 `payment_orders.user_id`의 not null을 해제한다.
  - user_id가 없는 주문은 이 랜딩 주문뿐이다. 이용권 지급·코인 회수·결제완료 알림톡처럼 user_id를 쓰는 곳은 모두 건너뛴다.
  - 빌더는 `user_id`·`userId`를 쓰는 곳을 **전부 grep** 해서 null 처리를 확인한다.
- 무통장 주문은 `payment_orders`에 넣지 않는다. 그래서 대시보드 매출에 빠지며, 이것을 알려진 한계로 기록한다. 관리자 주문 화면에 무통장 입금 합계를 따로 보여준다.

### 6-3. 결제
- 카탈로그에 새 상품 2개를 둔다(사주 주소 불필요, 다른 화면 목록에는 노출 안 함). 정가는 `compareAt`으로 표시하고, 가격은 관리자 가격 화면에서 바꿀 수 있게 기존 구조를 따른다.
- prepare에 랜딩 상품 분기를 둔다.
  - 로그인 검사 앞에서 갈라진다.
  - 쿠폰·이용권 검사와 회원 동의 기록은 건너뛴다.
  - 동의는 `report_orders`에 동의 시각·약관 버전으로 남긴다.
  - 금액은 서버 카탈로그에서만 정한다. 화면이 보낸 금액은 믿지 않는다.
- 나이스페이 return: 이 상품이면 지급 없이 주문을 `paid`로 바꾸고 비회원 완료 화면으로 보낸다. 기존 서명 검증은 그대로 둔다.
- 나이스페이 취소 통보(웹훅): user_id가 없는 주문은 코인 회수를 건너뛰고 `report_orders`를 `refunded`로 바꾼다.
- 남용 방지: 주문서 요청은 같은 IP 기준으로 횟수 제한(기존 방식이 있으면 재사용), 본문 크기 제한, 같은 출처만 허용.

### 6-4. 무통장 입금
- 계좌 정보(은행·번호·예금주)는 환경변수로 둔다. 없으면 무통장 선택지를 숨긴다.
- 입금 기한은 주문 후 3일(빌더 판단). 기한이 지나면 관리자 목록에 "기한 지남"으로 표시하고, 취소는 관리자가 누른다(자동 취소 없음).
- 현금영수증: 주문서에 "현금영수증 신청" 선택 칸을 둔다(번호는 휴대폰 번호 기본). 발급은 관리자가 홈택스에서 직접 한다. ⚠️ 의무 발행 업종 여부는 확인 필요.

### 6-5. 관리자 주문 화면 (`/admin/report-orders`, super_admin)
- 목록 필터: 입금 대기, 결제 완료, 확인 대기, 발송 완료, 취소·환불
- 주문마다 할 수 있는 일
  - 입금 확인 (무통장)
  - 풀이 만들기: 기존 `generateExternalReport`·`generateExternalNewYearReport`를 그대로 쓰고, 결과는 기존 `admin_external_reports`에 저장한다
  - 미리보기: 기존 화면 재사용
  - 확인 완료·발송
  - 다시 보내기, 취소
- AI 실패로 기본 문구가 섞이면(`generationWarning`) 발송 버튼 옆에 경고를 띄우고 "다시 만들기"를 권한다.
- 관리자 왼쪽 메뉴의 "운영 도구"에 추가한다.

### 6-6. 손님 결과 링크 (`/r/[token]`)
- 토큰으로 `report_orders`를 찾는다. `sent` 상태일 때만 snapshot을 기존 `ExternalReportView`로 그린다. AI는 다시 부르지 않는다.
- 화면에 "PDF로 저장" 버튼을 둔다(브라우저 인쇄, 기존 방식).
- 검색 노출 금지(noindex), 공유 미리보기에 이름·생년월일을 넣지 않는다.
- 토큰이 틀리거나 상태가 아니면 같은 "찾을 수 없음" 화면을 보인다(존재 여부를 드러내지 않음).
- 링크 유효기간은 보관 기간(§7)과 같다.

### 6-7. 발송
- 문자: Solapi 일반 문자(`solapiSendText`, 템플릿 심사 불필요)로 결과 링크를 보낸다. 접수 확인과 무통장 입금 안내도 문자로 보낸다.
- 이메일: Resend(`sendNotificationEmail` 계열)로 같은 링크를 보낸다. PDF 첨부는 하지 않는다(첨부 크기·스팸 문제).
- 발송 실패는 주문 화면에 표시하고 "다시 보내기"로 해결한다. 문자와 이메일 중 하나만 성공해도 `sent`로 둔다.

### 6-8. 취소·환불 (작성자 판단)
- 카드: 관리자 주문 화면의 "결제 취소" 버튼이 기존 나이스페이 취소 함수를 직접 부르고, 주문을 `refunded`로 바꾼다.
  - 회원 환불 표(`refund_requests`)는 user_id가 필수라 쓰지 않는다. 마이그레이션을 늘리지 않기 위해서다.
  - 나이스페이 관리 화면에서 직접 취소한 경우에도 취소 통보(웹훅)가 상태를 맞춘다.
- 무통장: 손님 계좌는 문자·전화로 받아 관리자가 직접 이체한다. 시스템에는 "환불 완료" 표시와 메모만 남기고, 계좌번호는 저장하지 않는다.

### 6-9. 태어난 시간 (작성자 판단)
- 시간대 선택 13칸에 "모름"을 더한다. 자시는 "밤 11:30~자정"과 "자정~새벽 1:29" 두 칸으로 나눠 날짜가 흔들리지 않게 한다.
- 각 칸은 대표 시각으로 바꿔 기존 생성기에 넘긴다.
- 출생지는 받지 않고 기존 기본값(표준시)으로 계산한다. 관리자 PDF 화면의 기본 계산과 같다.

### 6-10. 보관과 삭제 (작성자 판단, §9-6에서 사용자 확인)
- 발송 1년 뒤 `report_orders`에서 지우는 것: 이름·연락처·생년월일·메모·결과 토큰. 이때 결과 링크도 끊긴다.
- 남기는 것: 주문번호·상품·금액·결제 수단·날짜. 거래 기록은 5년간 보관한다. ⚠️ 전자상거래법 기간 확인 필요
- 연결된 `admin_external_reports` 풀이 원본도 1년 뒤 함께 지운다.
- 삭제는 하루 한 번 도는 크론으로 한다.

## 7. 개인정보·약관

- 비회원 주문 때문에 수집 항목이 늘어난다(휴대폰·이메일·생년월일시·이름). 개인정보처리방침을 고쳐야 한다.
  - 정책 본문은 **DB 새 버전 발행**으로 고친다. 번들 버전을 올리면 운영 방침을 덮는 사고 이력이 있다.
  - 보관 기간: 발송 후 1년(빌더 제안, 사용자 확인). 전자상거래법상 거래 기록 보관 의무는 별도로 지킨다.
- 결과 링크와 관리자 화면 외에는 주문자 정보를 노출하지 않는다. 로그·퍼널 기록에 이름·생년월일·연락처를 남기지 않는다.

## 8. 검증 (완료 기준)

- 단위 테스트
  - 주문서 검증(필수 항목·형식·길이)
  - 금액은 서버 카탈로그 값만 쓰는지
  - user_id 없는 주문이 지급·회수·알림톡을 건너뛰는지
  - 상태 전이(허용되지 않은 전이 거부)
  - 토큰 조회는 `sent`만 보이는지
- 실화면(390px)
  - 랜딩 전체 넘침 없음
  - 주문서 → 나이스페이 결제창 금액 일치(실결제는 사용자 확인)
  - 무통장 주문 → 입금 확인 → 생성 → 발송 → 결과 링크 열림 → PDF로 저장
- 기존 기능 회귀: 회원 결제·이용권·환불 테스트 전부 통과, `npm test`·`test:spec`·tsc·build
- 머지 전 보안 검토(RLS·토큰·비회원 결제 경로)와 Codex 교차 검토(사용자 채택 흐름)

## 9. 남은 것

- **후기 원문**: 사용자가 보내 주기로 했다. 받기 전까지 후기 칸은 숨긴다.
- **AI 사용 고지**: 기존 `/ai-disclaimer`를 랜딩 하단과 결과 화면에 연결한다(작성자 판단). 인공지능기본법상 고지 의무가 어디까지인지는 ⚠️ 검증필요.
- **보관 기간**: 발송 1년 뒤 삭제(§6-10, 작성자 판단)이고, 사용자가 다르게 정하면 바꾼다.
- **신년운세 쪽수**: 구현 때 실측해 문구에 반영한다.
