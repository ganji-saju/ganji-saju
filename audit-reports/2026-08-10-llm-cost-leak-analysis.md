## 2. 🔴 누수 #1 — 총평 재시도 (전체 비용의 약 50%)

### 실측
07-04~07-29 깨끗한 구간, 3분 간격으로 버스트를 리포트 단위로 묶어 계산:

| 항목 | 값 |
|---|---:|
| 리포트 수 | 89 |
| 실제 LLM 콜 | 765 |
| **리포트당 중앙값** | **8.0 콜** |
| 구조상 최대 | 9 콜 (3섹션 × 3시도) |
| 필요한 콜 | 267 (89 × 3섹션) |
| **낭비된 콜** | **498 (65%)** |
| 비용 | $7.257 |
| **낭비 비용** | **≈ $4.72** |

중앙값 8이 최대 9에 붙어 있다 = **거의 모든 섹션이 재시도를 소진**하고 있다.

### 원인 (a) 금지어가 `includes()` 부분문자열 매칭 — 일상어를 학살한다

`src/lib/saju/total-review-validator.ts:84` — 금지어 42개·자극어 8개를 전부 `text.includes(term)`으로 검사. 한국어에서 이 단어들은 무해한 복합어의 부분문자열이다. 실측:

| 자연스러운 문장 | 판정 | 걸린 단어 |
|---|---|---|
| 주변의 **지지**를 받으며 자라온 편이에요 | ❌ 폐기 | 지지 (地支) |
| 남의 평가에 크게 **상관**없이 움직입니다 | ❌ 폐기 | 상관 (傷官) |
| 실수에도 **관대**한 편이라 편하게 다가옵니다 | ❌ 폐기 | 관대 (冠帶) |
| 악기를 **연주**하듯 리듬을 맞추는 방식 | ❌ 폐기 | 연주 (年柱) |
| 이미 결**정인** 사안은 빠르게 넘어갑니다 | ❌ 폐기 | 정인 (正印) |
| **반드시** 지켜야 할 원칙 하나를 정해두면 | ❌ 폐기 | 반드시 (자극어) |

**6문장 중 6문장 오탐 폐기.** 성격 풀이에서 "지지받는", "관대한", "상관없이"는 지극히 자연스러운 어휘다. 모델은 정상적인 한국어를 썼다는 이유로 계속 탈락한다.

> 참고: 프롬프트 §3의 금지어 목록은 더 위험하다(`합`·`충`·`형`·`파`·`해` 포함). 검증기 목록에는 없어 최악은 피했지만, 프롬프트가 모델에게 과도한 회피를 요구하는 구조는 동일하다.

### 원인 (b) 재시도가 완전히 동일한 프롬프트를 다시 보낸다

`src/server/ai/generate-total-review.ts:83`:

```ts
for (let attempt = 0; attempt <= maxRetries; attempt++) {
  raw = await client.generate(TOTAL_REVIEW_SYSTEM_PROMPT, userMessage);  // ← 매번 동일
  ...
  const validation = validateTotalReviewSection(sectionId, parsed);
  if (validation.ok) return ...;
  lastReasons = validation.reasons;   // ← 저장만 하고 다음 시도에 안 씀
}
```

`lastReasons`를 담아두지만 **다음 시도 프롬프트에 넣지 않는다.** 모델은 자기가 뭘 틀렸는지 모른 채 같은 질문을 세 번 받는다. 재시도는 확률이 개선되지 않는 독립 시행 — 순수한 주사위 굴리기다.

### 원인 (c) 프롬프트 지시와 검증기 기준이 어긋나 있다

- 프롬프트: "각 단락 5~8문장" × 4단락 = **20~32문장 허용**
- 검증기(`total-review-validator.ts:160`): **25~35문장 요구**
- → 모델이 지시를 정확히 지켜 단락당 5~6문장을 쓰면 20~24문장 = **탈락**

저장된(=통과한) 67건의 실제 문장 수 분포가 이를 증명한다:

| min | p25 | median | p75 | max | 밴드 내 | 밴드 미만 | 밴드 초과 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 25 | 26 | 27 | 28 | 30 | 67 (100%) | 0 | 0 |

**전부 하한(25)에 붙어 있고 상한 근처는 하나도 없다.** 생존자 편향 — 25 미만은 전부 폐기됐다는 뜻. 이 밴드가 결정적 병목이다.

### 원인 (d) 시스템 프롬프트가 금지어를 스스로 3번 사용한다

`TOTAL_REVIEW_SYSTEM_PROMPT` 규칙 8·9·[밀착 개인화] 항목이 **"반드시"**를 3회 쓴다. 그런데 "반드시"는 `CLICKBAIT_ABSOLUTE` 금지어다. 프롬프트가 모델에게 그 단어를 반복 노출시켜 출력에 새어나올 확률을 스스로 높이고 있다.

## 3. 누수 #2 — yearly 프롬프트 비대 (비용의 13%)

- 콜당 **입력 22,702 tok / 출력 1,158 tok = 19.6 : 1**
- yearly 비용의 **71%가 입력 측**

`lifetime`도 동일 패턴(입력 27,566 / 출력 1,613 = 17:1, 입력이 비용의 68%)이나 캐시율 79.2%로 방어되고 있어 총액은 작다.

## 5. 누수 #4 — 계측 공백 (돈이 아니라 눈)

1. **`total_review`는 `user_id_hash`가 100% NULL** (832콜 전부). 비용 82%를 쓰는 기능이 사용자 귀속이 안 된다 → 누가·몇 번 재생성하는지 추적 불가. `chapter`도 100% NULL.
2. **프롬프트 캐시 적중을 기록하지 않는다.** OpenAI Responses API는 `usage.input_tokens_details.cached_tokens`를 주는데 `openai-text.ts`가 추출하지 않는다 → 반복 프리픽스가 실제로 캐시되고 있는지 **알 수 없다**.
3. **재시도가 텔레메트리에서 안 보인다.** 실패한 시도도 `source='openai'`로 기록되므로 성공/폐기 구분이 불가. 이번 분석도 버스트 추론으로 우회했다.

## 8. 이 분석의 한계 (확정 vs 추론)

**측정된 사실:**
- 기능별 토큰·비용·캐시율 (§1) — DB 집계
- 리포트당 8콜 중앙값 (§2) — DB 버스트 집계
- 통과 출력의 문장수가 하한에 밀집 (§2c) — DB 실측 67건
- 금지어 부분문자열 오탐 (§2a) — 실제 검증기 목록으로 재현
- 재시도가 동일 프롬프트 재전송 (§2b) — 코드 확인

**추론 (직접 측정 못 함):**
- **어떤 규칙이 재시도를 얼마나 유발했는지의 정확한 배분.** 실패한 시도의 출력·사유가 저장되지 않아(§5-3) 직접 셀 수 없다. §2a·§2c가 주 원인이라는 건 "중앙값 8/최대 9" + "통과분이 하한 밀집" + "오탐 재현"의 정황 조합이다.
- §2a의 예시 6문장은 실제 폐기된 출력이 아니라 재현용으로 작성한 문장이다.
- **처방 후 효과 추정치는 검증 전 예측이다.** 조치 1~4 적용 후 같은 버스트 집계를 다시 돌려 실측 확인이 필요하다.

**전제:** 절대 금액은 작다 (9주간 $9.26, 월 $15 내외). 의미 있는 건 **비율**이며, 트래픽이 늘면 그대로 확대된다. 지연시간 25초 → 10초 개선이 금액보다 큰 가치일 수 있다.
